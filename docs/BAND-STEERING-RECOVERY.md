# Band Steering: recovery without restart (проєкт)

Статус: **проєкт, не реалізовано**. Поведінка пристрою не змінювалася.

## Навіщо

Зараз будь-яка помилка циклу завершує демон (`loop.c` → `fault()`), а
координатор не має API пересинхронізації (`coordinator.h`: init/tick/event/
stop/fault). Через це `ENOBUFS`, обрізана подія або втрата listener-сокета
вимикають стірінг до перезавантаження.

## Класи відмов

| Клас | Ознака | Поточна дія | Пропонована дія |
| --- | --- | --- | --- |
| Переповнення черги | `ENOBUFS` на receive | exit | дренувати + resync |
| Пошкоджена подія | truncated/malformed | exit | пропустити + resync |
| Втрата listener | `POLLHUP`/`POLLERR` | exit | перевідкрити + resync |
| Жорсткий збій | сигнал/OOM | exit | supervisor (окремо) |

## Що потрібно додати

1. `wr_band_coordinator_resync()` — скидає похідний стан координатора до
   стану «немає даних» і вимагає свіжого знімка драйвера.
2. Запит повного стану драйвера (кількість BSS, активні клієнти, таблиця
   grant) — зараз є лише потік подій.
3. Guard: поки resync не завершено, **жодних** команд стірінгу не
   відправляти; будь-яка спроба — помилка.
4. Обмеження: якщо resync не вдався N разів (наприклад, 3), демон завершується
   з `fault()` — далі діє supervisor/повторний запуск.

## Порядок recovery

1. Зафіксувати причину в syslog (`errno`, `revents` — уже є в `c8bce32`).
2. Дренувати сокет до `EAGAIN` (для `ENOBUFS`) або перевідкрити listener
   (для `POLLHUP`).
3. Викликати `resync()` і дочекатися повного знімка.
4. Відновити політику з того самого профілю налаштувань.
5. Лише після успіху — знову обробляти події.

## Кодова перевірка (2026-10-22)

- `listener.c`: `wr_band_listener_open()` створює новий netlink-сокет і не має
  внутрішнього стану, тому після `close()` його можна викликати повторно —
  перевідкриття listener-а технічно можливе.
- `coordinator.c`: `wr_band_coordinator_init()` робить `memset()` і заново
  ініціалізує clients/policy/grants/aging/session з переданими конфігом і
  політикою. Це готовий «reset», але після нього координатор не має даних про
  клієнтів — їх треба відновити зі свіжого знімка драйвера.
- Отже єдиний відсутній блок — **запит повного стану драйвера**. Без нього
  resync неможливий; з ним recovery зводиться до: close listener → open
  listener → coordinator_init → повний знімок → продовження циклу.

## Тести (host fixture)

- `ENOBUFS` → дренаж, resync, цикл продовжується, команди стірінгу до
  завершення resync не надсилаються;
- обрізана подія → пропуск + resync;
- `POLLHUP` → перевідкриття listener + resync;
- три невдалі resync → `fault()` (демон завершується, далі supervisor);
- штатний STOP → без recovery.

## Межі

- Recovery не рятує від `SIGKILL`/OOM — для цього потрібен supervisor.
- Без реального драйверного запиту стану recovery неможливий: потрібно
  підтвердити, що MT76 expose-ить достатньо даних для повного знімка.
- Усе це потребує перевірки на пристрої; host-фікстури доводять лише логіку.
