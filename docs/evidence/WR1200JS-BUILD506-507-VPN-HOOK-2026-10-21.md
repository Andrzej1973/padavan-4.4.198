# WR1200JS builds #506–#508 — VPN capability hook mismatch

GitHub Actions firmware runs [#506](https://github.com/Andrzej1973/padavan-4.4.198/actions/runs/39615356036)
(`25ca366`) and [#507](https://github.com/Andrzej1973/padavan-4.4.198/actions/runs/39615665030)
(`029b230`) failed in `Exclude legacy VPN userspace from WR1200JS`, before
firmware compilation. Both job logs end that step with `VPN index removal
changed: vpncli.asp`. The downstream downloads job failed because the selected
firmware build failed; there is no image verdict from these runs.

Run [#508](https://github.com/Andrzej1973/padavan-4.4.198/actions/runs/39616322625)
(`e806465`) subsequently failed in the same pre-compilation step. It was
started from a commit that predates the hook correction. The fix first appears
in `63dfd1d`, with the prepared-page gate added in `fe02f7e`.

`prepare-wr-vpn-pruning.py` required the old
`document.form.vpnc_type.remove(2)` index hook. Both current Classic VPN pages
already contain an exact value-based OpenVPN capability hook:
`$j("#vpnc_type option[value='2']").remove()` and its `vpns_type` counterpart.
The earlier `prepare-web.py` removes the unavailable PPTP/L2TP options, but
does not change these hooks. The later pruning step must preserve an existing
value-based hook or upgrade exactly one old index hook. Missing, duplicated or
mixed hooks fail closed.

Local Python syntax checks, exact overlay client/server hook checks and
positive/negative hook fixtures passed. The `Exclude legacy VPN userspace from
WR1200JS` preparation step subsequently completed successfully in
[#509](https://github.com/Andrzej1973/padavan-4.4.198/actions/runs/39616980846)
(`63dfd1d`), [#510](https://github.com/Andrzej1973/padavan-4.4.198/actions/runs/39617283181)
(`fe02f7e`) and [#511](https://github.com/Andrzej1973/padavan-4.4.198/actions/runs/39618043514)
(`2e73d22`). This confirms that the original pre-compilation blocker is fixed.
All three runs later failed in `Resolve names through the image Stubby under
QEMU`: the final combined-config `dnsmasq --test` invocation under
`qemu-mipsel-static` exited 5 after printing `dnsmasq: failed to seed the
random number generator: Success`. The preceding encrypted-DNS checks passed,
including authenticated Stubby DNS-over-TLS queries, strict-mode behavior when
TCP/853 was blocked, recovery, and DNS listener-conflict fixtures. The failure
also caused the selected-image requirement in the downloads job to fail; its
index reports `images: []` and `image_status: missing-or-ambiguous`, so no
verified downloadable firmware image is available from these runs. The StrongSwan image
diagnostic upload also failed because its expected JSON file was absent after
the earlier failure. This later failure is separate from the now-passing VPN
preparation step. A follow-up inspected the exact pinned dnsmasq 2.90 source:
`config.h` sets `RANDFILE` to `/dev/urandom`, and `util.c` seeds its SURF state
by reading 128 bytes followed by 48 bytes. The error text ending in `Success`
indicates the fatal path did not have a useful errno, consistent with a short
read from the image-root's `/dev/urandom` placeholder under QEMU. This is a
test-environment diagnosis, not evidence of a bad dnsmasq configuration or a
router DNS defect.

The checker now constructs a temporary QEMU sysroot overlay: ordinary target
root entries resolve to the built image, while `/dev/urandom` is a bounded
file seeded from the CI host CSPRNG and the generated config is exposed under
guest `/tmp`. It does not modify ROMFS or the device. Python AST parsing and
`git diff --check` pass locally. The target-binary QEMU rerun is still pending;
do not call this blocker fixed until the workflow succeeds and a downloadable
image is verified.

The prepared-source verifier now also requires exactly one value-based hook
on both client and server pages and rejects the obsolete index hook. This is
source verification only; it does not prove browser execution or router state.
