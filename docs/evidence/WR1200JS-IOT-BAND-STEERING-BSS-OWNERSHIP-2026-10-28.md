# IoT MBSS Band Steering ownership — 2026-10-28

Scope: pinned MT76x3 source at `c25283e915a2a00a763774dd255b14aff997285e`, and the isolated, nonproduction v14 composition. This is a source audit, not a target compile or router result.

`ap/ap_band_steering.c:BndStrg_SetInfFlags` is **per wifi_dev**, rather than one boolean for a whole band. It updates `wdev->bInfReady`, changes the table's `ActiveCount`, records `wdev->func_idx`, and sends an `INF_STATUS_RSP` carrying `wdev->if_dev->name`. Its own comments say it runs for each interface up/down. `Set_BndStrg_Enable` walks active MBSS entries and publishes each separately. Therefore the earlier handoff statement that a secondary MBSS must never publish readiness because the flag is band-wide is incorrect. Removing the IoT BSS notification without a replacement could leave the daemon's per-interface state stale.

The current v14 composition also cannot retain the vendor call unchanged: `ap/ap_mbss.c:MBSS_Open` publishes `TRUE` during `CMD_RTPRIV_IOCTL_MBSS_OPEN`, before `VIRTUAL_IF_UP_CLAIM`, `CMD_RTPRIV_IOCTL_MBSS_CR_ENABLE`, observation and registry commit in `include/wr-iot-mbss-open-admission.inc`. A failed open could therefore announce a ready interface that never opened. `MBSS_Close` publishes `FALSE` before the checked close executor has completed `wr_iot_virtual_down_checked`; a failed DOWN could announce an offline interface that remains owned. The abort path must not set `FALSE` unless it can prove a matching `TRUE` was published for the same generation.

Next candidate: give per-BSS ready/down messages an explicit committed owner and generation. Publish ready only after a successful claimed open and ownership/readback decision; publish down only after successful checked DOWN/consume. Preserve ordering against concurrent close/reset and daemon enable/disable, without sending a daemon event under `wr_iot_transition_lock`. Add host failure/race fixtures before target compilation. The source gate now reports the premature vendor call accurately; it still fails v14 as intended. No production driver, firmware image or router state was changed.

The source gate also requires relocated ready and down publications in the checked open admission and close executor after the premature vendor calls are removed. This prevents a source-only candidate that silently drops the IoT BSS daemon events from passing. Presence is a necessary source preflight, not evidence of event ordering, daemon delivery or runtime behavior; those still require the focused failure/race fixtures and device acceptance.

## Isolated v15b ready-publication candidate

`tools/iot/prepare-mbss-steering-ready-candidate.py` checks every input file against the v14 composition manifest and emits `.iot-local-check/mt7603-main-recovery-mbss-ready-v15b-20261028` with 67 matching hashes and `production_installed=false`. It changes only `ap/ap_mbss.c` and `include/wr-iot-mbss-open-admission.inc`. The first draft v15 excluded all MT7603 BSS from the vendor notification while its replacement covered only BSS1/BSS2; v15b narrows the exclusion to MT7603 BSS1/BSS2 when at least three BSS are configured. Other boards and additional BSS retain the vendor path. The replacement handles both BSS1 and BSS2 after raw claimed-UP/CR_ENABLE success, BSS observation, owned-reference publication and count check, while the BSS_OPEN ticket is still live. It releases the IRQ lock for the daemon event, then reacquires it before retiring the ticket.

The broad source gate now advances past the ready-publication check and fails at `MBSS closes per-BSS Band Steering state before checked DOWN completes`. This is the intended next gap. Source inspection and hash checks do not establish MIPS compilation, daemon ordering under concurrent Band Steering enable/disable, or router behavior. The checked close notification, failure/race fixtures, recovery owner and PCI release claim remain open. Do not install v15b.

## Isolated v16b down-publication candidate

`tools/iot/prepare-mbss-steering-down-candidate.py` verifies all v15b hashes and emits `.iot-local-check/mt7603-main-recovery-mbss-steering-v16b-20261028`. It changes only `ap/ap_mbss.c` and `include/wr-iot-mbss-close-checked.inc`; all 67 output hashes match, and `production_installed=false`. For MT7603 BSS1/BSS2 with at least three BSS configured, it suppresses the early vendor down notification and calls a per-BSS helper only after `wr_iot_virtual_down_checked` returns success. The CLOSE or BSS_CLOSE ticket remains active, and the helper runs outside the transition IRQ lock. Other boards/BSS retain the vendor path. The earlier v16 draft has an imprecise ticket name in a source comment and is superseded by v16b.

The broad virtual-call gate now advances beyond both steering checks and stops at `radio ticket retirement wakeup coverage changed: include/wr-iot-mbss-open-admission.inc`. The candidate has no target compile, no failure/race fixture and no runtime proof. Next stage must account for every MBSS open path that retires or aborts a ticket, wake waiters after dropping the IRQ lock, and verify error paths and spurious wake safety. Do not install v16b.
