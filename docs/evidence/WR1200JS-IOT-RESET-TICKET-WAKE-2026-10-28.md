# Reset ticket wakeup — isolated v18, 2026-10-28

The v17 source `include/wr-iot-reset-admission.inc` retired a RESET ticket through `wr_iot_radio_finish_unverified` without waking `wr_iot_ticket_wait`. A blocked waiter could therefore remain asleep until timeout despite the transition becoming idle. The shared template `tools/iot/reset-admission.inc` now records the finish result and calls `wake_up_all` only when the ticket retired, after both `RTMP_IRQ_UNLOCK` and `rtnl_unlock`. A failed RTNL trylock or failed ticket begin does not wake and does not claim reset completion.

`tools/iot/prepare-reset-ticket-wakeup-candidate.py` verified all v17 source hashes and matched its one-file output against the shared template. Isolated `.iot-local-check/mt7603-main-recovery-reset-wake-v18-20261028` changes only `include/wr-iot-reset-admission.inc`; all 67 manifest hashes match, `production_installed=false`. The strict C11 host fixture `check-reset-admission.c` passed with `-Wall -Wextra -Werror`, including busy deferral, nested raw PSE/PDMA, retained reset request, explicit retry, four conditional wakes, no wake while a lock is held, and no readiness claim. Hardware was mocked.

`check-virtual-if-call-coverage.py` now passes the v18 tree and still rejects v17 for the missing reset wake. Its main-open wake check was narrowed to the `MainVirtualIF_open` body: the same source file also contains a valid main-close wake. Its caller expectation recognizes that the staged main checked-close executor uses `wr_iot_virtual_down_checked` instead of a direct `VIRTUAL_IF_DOWN` call. These source checks are necessary but do not prove target compilation, actual waitqueue interleavings, callback/PCI retirement, image contents or router runtime behavior. Continue with focused race/failure verification and the remaining recovery/PCI release gates before production installation.
