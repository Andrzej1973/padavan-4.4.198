# IoT main readiness reconciliation — isolated v20, 2026-10-28

The isolated v19 MBSS steering race candidate was derived from the recovery chain, not from the parallel v44 main-readiness candidate. Direct source comparison found that v19 `os/linux/rt_main_dev.c` had no `wr_iot_main_readiness_verify` producer after `MainVirtualIF_open`, although its MBSS admission required `main_ready`. This prevents treating v19 as an integrated activation candidate. It is a missing producer, not evidence that the radio is ready.

`tools/iot/prepare-main-readiness-verify-candidate.py` now accepts the reviewed later composition, which puts the shared claim helper in a different include location. It retains the original include anchor for the earlier v43 path and uses the unique `rt_os_net.h` anchor only when the explicit claim include is absent. Running it on v19 generated `.iot-local-check/mt7603-main-recovery-steering-verify-v20-20261028`. The output has the same 67 files as v19; byte hashes differ only for `os/linux/rt_main_dev.c`. The generated manifest says `production_installed=false`, `main_readiness_verify_bound=true`, `recovery_owner_bound=false`, and `pci_release_gate_bound=false`.

The focused main-readiness checker passed: VERIFY admission, unlocked beacon/queue observation, locked ticket/generation/count revalidation, and HNAT/queue ordering. The broad virtual-interface source gate passed. The strict C11 MBSS post-open host fixture passed guest/IoT and reset/readback cases, and `check-virtual-open-claim.c` passed ownership/count/ticket cases. These are host/source checks with mocked hardware; no MIPS target compilation, finished firmware image or router test has been run for v20.

Do not package or install v20. The failed VERIFY path still returns an `ndo_open` failure after a claimed virtual UP and retains the owner; the deferred recovery owner and PCI release fence remain unbound. The main-readiness observer checks configuration and register intent, not emitted RF frames or client connectivity. Resolve the retained-owner recovery path and target compilation before device acceptance.

Recovery call-site audit: v20 has a `wr_iot_main_recovery_work_fn` and a checked close executor, but no caller of `wr_iot_main_recovery_queue`, `wr_iot_main_recovery_schedule_result`, or `schedule_work` for this owner. The failed `VERIFY` branch therefore retains the module/virtual-UP owner without starting recovery. The executor calls checked close without taking RTNL. Main `ndo_open`/`ndo_stop` normally run under RTNL, while `rt_pci_remove` calls `cancel_work_sync` during teardown. A worker that blocks in `rtnl_lock` while removal joins it can deadlock; a worker that proceeds without an RTNL/lifetime contract is also unproven. Next integration must jointly establish a netdev hold, adapter-release fence, RTNL-safe worker admission, exact queued/schedule-result accounting, bounded retry or retained-owner handling, and a remove path that joins and releases those owners. Merely wiring `schedule_work` is not sufficient. This is a source finding; no worker was scheduled or executed on the router.

Focused host transition fixture: `tools/iot/check-main-verify-recovery.c` compiles with `gcc -std=c11 -Wall -Wextra -Werror` against v20 headers and passes. It begins a main open, records an acquired virtual reference, retires the open as unverified, fails the main VERIFY observation, and confirms that a secondary BSS cannot open. Recovery admission rejects missing netdev hold or adapter fence, then retains the exact device/generation/open token when both proofs are supplied. A rejected schedule preserves the owner and module pin; retry is accepted only after an external join proof, and the worker model selects checked close. This tests host state transitions only. It does not supply the missing driver queue call, actual `dev_hold`, RTNL-safe callback, or PCI lifetime proof.

The fixture now also sends that exact post-VERIFY `FAULT` state through `wr_iot_main_stop_request`; it admits a `WR_RADIO_CLOSE` ticket and moves the radio to `CLOSING` with `main_ready=0`. This closes the host-model gap between the recovery action decision and the shared close gate. The actual driver callback/worker ordering remains untested.
