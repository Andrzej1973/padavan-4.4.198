# MBSS steering intent race — isolated v19, 2026-10-28

The v18 MBSS wrapper held its BSS_OPEN ticket while publishing the per-BSS Band Steering ready event, but reset/main-down intent can latch under the transition lock without waiting for that ticket. `wr_iot_radio_request_reset_kind` advances the epoch, sets `reset_pending` and clears `main_ready`. The strict host fixture reproduced the defect: a reset injected during BSS readback left `reset_pending` set yet the v18 wrapper still called the ready publisher. That fixture failed at its `ready_calls==0` assertion. No router action was involved.

`tools/iot/prepare-mbss-steering-race-candidate.py` verifies the v18 source manifest and emits `.iot-local-check/mt7603-main-recovery-steering-race-v19-20261028`, changing only `include/wr-iot-mbss-open-admission.inc`. All 67 output hashes match; `production_installed=false`. Before ready publication the wrapper checks the ticket epoch, READY phase, main readiness, reset/close/retire and PM intents under `wr_iot_transition_lock`. It unlocks for the daemon call, relocks and repeats the intent check. If intent latched during the call, it unlocks, publishes the matching per-BSS down status, then relocks before completing the BSS_OPEN ticket. The existing owned reference and unverified/fault handling remain in place.

The strict C11 host fixture (`-Wall -Wextra -Werror`, hardware mocked) passes on v19. It covers normal guest/IoT ready events; no ready event on failed readback, count mismatch, reset during readback, or partial raw-open errors; and one compensating down event for reset or main-down injected during ready publication. `check-virtual-if-call-coverage.py` accepts v19 and rejects v18 at missing checked steering compensation. This fixture models only the wrapper and ticket state. It does not prove daemon delivery, atomic visibility to clients, MIPS compilation, callback/PCI retirement or live router behavior. A brief ready-then-down notification remains possible when intent arrives during the daemon call; the protocol must tolerate this and device acceptance must verify convergence. Do not install v19.

Follow-up source check: `ap/ap_mbss.c` calls `BndStrg_SetInfFlags` for the individual BSS and `tools/band-steering/events.c` decodes the MT76x3 interface name. However, the staged userspace `wr_band_session_event` in `tools/band-steering/session.c` ignores MT76x3 events whose interface name differs from its configured radio name; `check-session.c` configures `ra0` and `rai0` and already checks that a `ra1` ready event does not update `ra0`. Consequently this host fixture cannot establish how a secondary `ra1`/IoT `ra2` event is consumed by a running daemon. The userspace coordinator is itself staged, not installed in firmware. The delivery/convergence and IoT exclusion policy need an explicit integration test with the actual driver table and service before claiming Band Steering compatibility. The project scope requires Band Steering OFF for IoT by default; a per-BSS driver notification is not proof that IoT clients should be steered.
