## Чинне рішення власника — 2026-11-24

Для WR1200JS поточна мета — стабільна прошивка Classic з основною та
гостьовою Wi-Fi. Ізольовану мережу IoT (ra2) вилучено з поточного обсягу
випуску, включно зі сторінкою, збереженням, застосуванням і завантаженням
IoT-профілю. Звичайні налаштування та служби Classic слід зберігати.
Основний образ для цього роутера — без CAKE/SQM. Окремий варіант із
CAKE/SQM (заводський OFF) залишається в плані випуску.

Збирати WR1200JS через Standard lane. IoT overlay та його налаштування,
вихідний код, тести, результати CI й діагностика залишаються в архіві
розробки. Пункти нижче, які вимагають IoT у релізі або ставлять його
першим пріоритетом, замінено цим рішенням. Докладно див.
[звіт про призупинення IoT](docs/runtime/WR1200JS-IOT-SUSPENSION-2026-11-24.md).

# AGENTS.md — Padavan Project Rules

## Чинне рішення власника — 2026-11-22

із CAKE/SQM (заводський OFF) і без CAKE/SQM. IoT обов’язковий в обох.

## 3. Пріоритети проєкту
1. **IoT Wi-Fi** — головний пріоритет.
2. **WR1200JS Classic-only release** — прийняти два профілі: Classic із
   CAKE/SQM (заводський OFF) і Classic без CAKE/SQM. Classic залишається в
   обох образах. Hybrid Modern не входить до поточного firmware scope.
3. Перейти до Mi Mini після WR1200JS acceptance за чинним двопрофільним scope.

Усі підтримувані плати повинні мати Main, Guest та IoT Wi-Fi. Не додавати конфігурацій, які виключають IoT.

IoT є обов'язковим у двох релізних профілях і керується через Classic.
Recovery-образ без ізольованого IoT payload є окремим recovery-кандидатом,
а не завершеним релізним профілем. Прошивання, перезавантаження та інші зміни
роутера потребують окремого дозволу.

## 4. Обов'язкові вимоги IoT
- Дотримуватися контрактів vendor SDK MediaTek mt76x3 та реального володіння ресурсами.
- Зберігати роботу Main/Guest, MCU ACK protection, TX state machines і radio timing.
- Для звільнення DMA descriptor або повторної постановки skb перевіряти ring-cell identity, ownership і живе посилання на пакет.
- WCID сам по собі не ідентифікує DMA descriptor.
- Зберігати ra2 late-TxS recovery, software OFF та обмежені тайм-аути.
- Не заявляти про runtime-безпеку без відповідних доказів.

Основні матеріали: `docs/iot/WR1200JS-RA2-PS-RETENTION.md` та `WR1200JS-RA2-TXS-LE-DIAGNOSTICS.patch`.

## 5. Фінальні профілі WR1200JS

| Профіль | WebUI | CAKE/SQM |
|---|---|---|
| 1 | Classic | Так, заводський OFF |
| 2 | Classic | Ні |

Обидва профілі мають містити IoT, Band Steering, Zapret2, сумісність
налаштувань і доступ до роутера.

Профіль із CAKE має підтримувати явне ввімкнення/вимкнення. У профілі без
CAKE не повинно бути робочого вигляду його керування. Зберігати налаштування
користувача; заводський OFF не повинен перезаписувати збережений вибір.

Перевіряти кожен образ окремо: revision, toolchain, config, TRX size/SHA256, ROMFS, наявність функцій, WebUI та release gates. Фізичне приймання — окремий етап.

## 6. Збірки та перевірки
- Компіляція — у Linux filesystem.
- Локальні легкі перевірки — спочатку один worker; стежити за CPU, RAM і часом.
- Повні firmware/kernel/module builds — GitHub Actions.
- Не запускати дублікати активних CI-збірок.
- Не вважати перевірку джерел або host build доказом роботи на пристрої.
- Розділяти source, host, target, image та physical runtime evidence.

Для локальних перевірок меж, довжин і станів спочатку використовувати наявні `.nim` helpers. Запуск: `nim c -r <script>.nim`. Звіт — короткий PASS/FAIL та exit code.

## 7. Git та публікація
- Використовувати наявний SSH remote та спільні правила Git.
- Не застосовувати force-push, reset, clean, нові клони чи worktree.
- Перед push перевіряти весь outgoing commit range.
- Завершувати й перевіряти один логічний пакет змін, потім публікувати його одним push.
- Після push перевіряти точний remote SHA та відповідні CI runs.
- Standard та optional CI — окремі lanes; результати зараховуються лише для точного SHA та відповідних inputs.
- Не дозволяти subagents публікувати зміни самостійно.

## 8. CI
- Для невдалого run перевіряти оригінальний job log та diagnostic artifact.
- Монітор CI — лише підказка, не доказ причини помилки.
- Виправляти монітор лише за наявності конкретного відтворюваного дефекту; додавати regression fixture.
- Не створювати періодичних Codex wakeups, зайвих dispatch або автоматичних змін на основі CI-тексту.
- Не змінювати concurrency groups і правила черг без окремої необхідності.

## 9. WebUI та можливості плат
- Classic — єдиний WebUI WR1200JS у поточному firmware scope. Не вилучати
  Classic з образів.
- Hybrid Modern assets збережені як попередня робота, але не є частиною
  поточного образу чи активного delivery scope.
- Перед показом функції в WebUI перевіряти повний шлях для конкретної плати: kernel/driver, backend, NVRAM/defaults та фінальний образ.
- Непідтримувані функції не повинні виглядати активними або прийматися backend.
- Вести per-board capability manifest і перевіряти відповідність `.config`, ROMFS та WebUI.

## 10. Очищення та безпека
- Після завершення кожного етапу інвентаризувати тимчасові файли та прибирати лише доведено непотрібні.
- Не видаляти source, незавершену роботу, докази, резервні копії, дані користувача чи файли з невідомим призначенням.
- Перед видаленням перевіряти точні шляхи, власника та активне використання.
- Не змінювати sudoers, системні proxy settings, права доступу або облікові дані без окремого дозволу.
- Діагностика роутера — лише через погоджений read-only helper. Будь-які зміни стану пристрою потребують явного дозволу.
